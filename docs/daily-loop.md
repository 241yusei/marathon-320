# 毎日のループ（Slack ↔ GitHub Issue ↔ js/data.js）

2026-09-03 導入。**このファイルが、定時に起動する私（コーチ）の作業手順書。**
3つの Routine（cron）はこのファイルを読む前提で書いてあるので、
運用を変えるときはプロンプトではなく **ここを直す**。

## なぜこの形なのか

私は常駐できない。Claude のコンテナは非活動で回収されるので、
Bot のようにチャットを見張り続けることが原理的にできない。
だから「本人の書き込みを GitHub Issue に置いておき、次の定時起動が読みに行く」形にした。

Slack は**窓**であって実体ではない。実体は常に GitHub Issue。
GitHub 公式 Slack アプリが双方向なので、Slack のスレッドに書けば Issue にコメントが入る。
Slack が落ちても、GitHub アプリからでもメール返信からでも同じ Issue に届く。

```
  07:00  私 → Issue を立てる ──────→ Slack に流れる
                                        ↓ 本人がスレッドに返信
                                     Issue にコメント
  21:00  私 ← コメントを読む ←────────┘
         → js/data.js を更新して main に push → GitHub Pages に反映
         → 所見を Issue にコメント ──→ Slack に流れる
```

## Issue の規約

- **1日1 Issue**。タイトルは `[日次] 9/4（金）` の形。日付は JST。
- 立てるのは朝の起動だけ。夜と翌朝は**同じ Issue にコメントする**（Slackで1日1スレッドになる）。
- 翌朝、前日の Issue を反映し終えたら `state: closed` にする。
- ラベルは使わない（リポジトリに存在しないラベルを渡すと落ちるため）。タイトルの `[日次]` で識別する。

## ① 朝 07:00 JST（cron `0 22 * * *` UTC）

1. `list_issues`（state OPEN）で `[日次]` の付いた**前日以前**の Issue を探す。
   - あれば `issue_read method=get_comments` で本人のコメントを読む。
   - **未反映のコメントがあれば先に②の手順4〜6を実行してから閉じる。**
   - コメントが1件も無ければ、そのまま閉じる（催促を持ち越さない。
     処方日を指定するほど実施率が下がるという実測があるため、しつこくしない）。
2. `js/data.js` を読む。`schedule` から**今日の曜日・月日に一致する行**を取る。
   `todayOne` が今日の日付でなければ、その行の内容で `todayOne` を書き換えて push する。
3. 今日の Issue を立てる。本文は下のテンプレ。

```md
## 今日やること
**（schedule の menu）**
（todayOne.sub / dist / zone を1行で）

> 必ず: （todayOne.must）

**なぜ**: （todayOne.why）

---
## 朝の記録（4項目・20秒）
このスレッドに返信してください。書き方は自由、抜けても構いません。

- 走る準備度（0〜10）
- 脚の張り（0〜10）
- 睡眠（時間 / 体感）
- 体重（測っていれば）

## 練習が終わったら
距離・時間・体感・平均HR（分かれば）。走らなかった日は、その理由を一言。
「気が乗らなかった」で構いません。理由が分かると設計を変えられます。
```

## ② 夜 21:00 JST（cron `0 12 * * *` UTC）

1. 今日の `[日次]` Issue を探す。無ければ何もせず終了（朝の起動が失敗している。
   その旨を1行だけ Issue を立てて残す）。
2. `issue_read method=get_comments` でコメントを読む。
3. **コメントが1件も無ければ**、短い催促を1回だけコメントして終了。
   すでに催促コメントを打っていたら**2回目は打たない**。
4. コメントがあれば `js/data.js` を更新する。
   - `dailyLog` に1行追記（`date` は `9/4` 形式）。`run` に練習の要点、`note` に所見。
   - ランがあれば `recentRuns` にも追記。
   - 朝の4項目が来ていれば `signals[0]` `signals[1]` の `value` / `judge` / `state` を更新。
   - 体重・睡眠・HRV・RHR が来ていれば `metrics` と `highlights` の該当行を更新。
   - `longRuns` の当日ぶんを実施していれば `done: true`。
   - **`todayOne` を明日のぶんに書き換える**（`schedule` の明日の行から）。
   - `meta.lastUpdated` を今日の日付に。
5. `node -e "global.window={};eval(require('fs').readFileSync('js/data.js','utf8'))"` で構文を確認。
6. **ファイルを個別に指定して** commit し、`main` に push する。`git add -A` は使わない。
7. Issue にコーチングの所見をコメントする。長くしない。3〜6行。
   - 良かった点を1つ、直す点を1つ、明日やることを1行。
   - 判定を変えたなら、その理由を1行。

## ③ 日曜 19:00 JST（cron `0 10 * * 0` UTC）

`CLAUDE.md` の「日曜夜に私がやること」4段をそのまま実行する。

```
① データの入力・分析 → ② 練習内容の見直し・翌週メニュー作成
→ ③ カレンダーにメニュー追加（終日「休み」を避ける）→ ④ js/data.js を見直す
```

- 受け取るのは **export.xml 由来の `health_1m.zip`**。GPX は受け取らない（`CLAUDE.md` 参照）。
- 抽出は `python3 tools/health_export_split.py <zip> -o health_monthly --months 1`。
- Google ドライブ／カレンダーの MCP は、定時起動のセッションでは
  **接続されていないことがある**。使えなければその旨を Issue に書いて、
  ファイルの受け渡しは Issue への添付に切り替える。GitHub は必ず使える。

## 全部の起動に共通する約束

- ブランチは `main`。PR は作らない（`CLAUDE.md` の公開方針）。
- `git add -A` / `git add .` は使わない。**ファイルを個別に指定する。**
  このリポジトリは public で、一度 push すると回収できない。
- 顔写真・診断書 PDF・施術記録はリポジトリに置かない。
- 判断基準は `CLAUDE.md` の「コーチング判断フレームワーク」に従う。
  単発の1データポイントで「即休養」と言わない。本人の主観申告をデータより軽視しない。
- **データが無い日は、無いと書く。** 推測で `dailyLog` を埋めない。
  欠測は `js/core/compute-datahealth.js` が拾ってサイトに出す。
- 迷ったら何もせず、Issue に「判断できなかった理由」を1行残す。
  間違った更新を push するより、保留の方が安い。
