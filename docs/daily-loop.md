# 毎日のループ（Slack #320 ↔ js/data.js）

2026-09-03 導入 / **2026-09-04 全面改訂**。
**このファイルが、定時に起動する私（コーチ）の作業手順書。**
3つの Routine（cron）はこのファイルを読む前提で書いてあるので、
運用を変えるときはプロンプトではなく **ここを直す**。

## 現在の形

```
  07:00  私 → Slack #320 に今日のメニューを投稿
                ↓ 本人はそのまま返信（アプリの切り替えゼロ）
  21:00  私 ← #320 を読む
         → js/data.js を更新して main に push → GitHub Pages に反映
         → 所見を #320 に投稿
```

- チャンネル: **#320** / `C0BUSHJ48R3`（ワークスペース `320-network`）
- 読み: `slack_read_channel` / `slack_read_thread`
- 書き: `slack_send_message`
- **GitHub Issue は使わない。** 本人が触る面は Slack だけ。記録は `js/data.js` の `dailyLog` が持つ

## ここに至るまでに潰した設計（同じ穴を掘らないために）

2026-09-03〜04 に実機で3つ試して、2つが死んだ。

| 試した形 | 結果 |
|---|---|
| **新規セッションで起動する Routine** | ❌ **リポジトリが1つも attach されない**（`folders_state: FOLDERS_STATE_NONE`）。空のコンテナで起動するので CLAUDE.md も読めず git も push できない。2回発火させて $1.07 / $0.95 を消費し、Issue も commit も0件。**しかも実行結果は `SUCCEEDED` と記録される。**成功したように見えて何も起きないのが最悪 |
| **GitHub Issue ＋ 公式 Slack アプリで双方向** | ❌ **Slack アプリは読み専用**。スレッドに返信しても Issue には入らない。実際に返信してもらって届かなかった。書き戻せるのは `/github open` `/github close` `/github reopen` だけ |
| **GitHub の通知メールに返信** | ❌ GitHub の MCP は本人のアカウント（241yusei）として動くので、私が立てた Issue も私のコメントも作者が本人になる。**GitHub は自分の書き込みを本人に通知しない**ので通知メールが飛ばない |
| **Slack コネクタ ＋ self-bind Routine** | ✅ 現行。`slack_read_channel` で直接読めるので、GitHub を経由する必要が最初から無かった |

**Routine は必ず self-bind**（`create_new_session_on_fire` を指定しない）で作る。
このコーチング会話に発火するので、リポジトリ・git の認証・Slack・GitHub・
Google カレンダー・ドライブが全部そのまま使え、文脈も引き継がれる。

代償が2つある。
1. `notifications`（スマホへのプッシュ）は self-bind では受け付けられない。
   → 通知は Slack への投稿そのものが担う。二重にしない。
2. **このセッションが終了すると Routine は止まる。**
   月に一度は `list_triggers` で `last_run` を見る。止まっていたら新しいセッションで
   同じ3つを作り直す（このファイルを渡せば再現できる）。

## ① 朝 07:00 JST（cron `0 22 * * *` UTC）

1. `slack_read_channel` で #320 の未読を読む。前夜以降に本人の書き込みがあれば、
   先に②の手順3〜5（`js/data.js` 更新 → push）を済ませる。
2. `js/data.js` の `schedule` から**今日の月日に一致する行**を取る。
   `todayOne` が今日の日付でなければ、その行の内容で書き換えて push する。
3. #320 に今日のメニューを投稿する。**長くしない。** 構成は次の4つだけ。

```
**9/5（土）｜イージー 5〜6km**
会話ペース・HR145以下

> 必ず: （todayOne.must）

なぜ: （todayOne.why を1〜2行で）
```

朝の記録（走る準備度・脚の張り・睡眠・体重）は**毎日は聞かない。**
聞くのは週2回まで。毎朝4項目を並べると、答えない日が続いたときに
「読み飛ばす画面」になる。

## ② 夜 21:00 JST（cron `0 12 * * *` UTC）

1. `slack_read_channel` で #320 を読む（`oldest` に前回処理した ts を渡す）。
2. 本人の書き込みが無ければ**何も投稿せずに終わる。**
   催促しない。処方日の走行確率が処方の無い日より低いという実測がある以上、
   催促は逆効果である可能性が高い。
3. 書き込みがあれば `js/data.js` を更新する。
   - `dailyLog` に1行追記（`date` は `9/5` 形式）。`run` に要点、`note` に所見
   - ランがあれば `recentRuns` にも追記
   - `longRuns` の該当行を `done: true` にし、`km` を実測値に置き換える
   - 実測が来た項目だけ `metrics` / `highlights` を更新する
   - **`todayOne` を明日のぶんに書き換える**
   - `meta.lastUpdated` を今日の日付に
4. `node -e "global.window={};eval(require('fs').readFileSync('js/data.js','utf8'))"` で構文確認。
5. **ファイルを個別に指定して** commit し `main` に push。`git add -A` は使わない。
6. #320 に所見を投稿する。**3〜6行。** 良かった点1つ、直す点1つ、次にやること1行。
   判定を変えたならその理由を1行。

### ワークアウトログの読み方

本人は Apple Watch のログをそのまま貼ってくる。拾うのはこの順。

1. **平均HR が上限（現在145）以下か** — これが最優先。ペースではない
2. **Z1-Z2 の割合** — ただし週20kmを下回る間は制約変数として扱わない（`CLAUDE.md`）
3. **心拍回復**（終了直後 → 1分後 → 2分後）— 速ければ「攻めても大丈夫」側のシグナル。
   2分で −30bpm 前後なら良好
4. **距離が直近30日の自己最長の +10% 以内か** — 超えていたら意図的な判断として記録する
5. ラップの散らばり — 中盤だけ速い等は処方との乖離として指摘するが、
   **心拍が上限内なら止める理由にはしない**

  判断に足るデータが無いまま処方を出さない。

## ★ 処方の出し方（2026-09-04 に実測で分かったこと）

**休養日を日付で指定しない。走る日も日付で固定しない。**

`CLAUDE.md` に自分で記録している数字がある。

> 処方日の走行確率 23.8% ／ 処方が無い日 37.3%。日付を指定すると13.5ポイント下がる。

それを知りながら「9/1〜2はラン休養」と日付で出し、**9/1 に 8.91km を走られた**。
本人の遵守の問題ではなく、処方の出し方の問題である。

- ✅「5〜6km を1本。9/5 か 9/6 のどちらかで」
- ✅「もう1本は脚が軽ければ。張っていれば休養に振替」
- ❌「9/5 に 6km」「9/1〜2 は休養」

**週の合計を埋めさせない。** 決めるのはロング走の刻みとイージーの本数だけで、
合計はそこから出てくる数字にすぎない。本数を減らしてよいと明示的に書く。

## 全部の起動に共通する約束

- ブランチは `main`。PR は作らない（`CLAUDE.md` の公開方針）。
- `git add -A` / `git add .` は使わない。**ファイルを個別に指定する。**
  このリポジトリは public で、一度 push すると回収できない。
- 顔写真・診断書 PDF・施術記録はリポジトリに置かない。
- 判断基準は `CLAUDE.md` の「コーチング判断フレームワーク」に従う。
  単発の1データポイントで「即休養」と言わない。主観申告をデータより軽視しない。
- **データが無い日は、無いと書く。** 推測で `dailyLog` を埋めない。
- **サイトの記録と実測が食い違ったら、実測を正として訂正し、訂正した事実を残す。**
  9/1 を「完全休養」と記録していたが実際は 8.91km 走っていた、という例が既にある。
- 迷ったら何もせず、#320 に「判断できなかった理由」を1行だけ残す。
  間違った更新を push するより、保留の方が安い。
