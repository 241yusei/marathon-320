## 現在の起動方式 — ローカル定時タスク（2026-09-04 移設）

クラウドの Routine は使わない。**self-bind は詰む。** 発火先が1つのチャットに固定
されるので、そのチャットを離れた瞬間に3本とも死ぬ。実際そうなって作り直しになった。
かといって `create_new_session_on_fire` は上の表のとおり空のコンテナで起動して失敗する。

代わりに **Mac 上のローカル定時タスク**を使う。実体は `~/.claude/scheduled-tasks/<id>/SKILL.md`。

| taskId | いつ | 何を |
|---|---|---|
| `marathon320-morning-slack` | 毎日 07:00 JST | このファイルの ① |
| `marathon320-night-slack` | 毎日 21:00 JST | このファイルの ② |
| `marathon320-sunday-review` | 日曜 19:00 JST | このファイルの ③ |

- 作業ディレクトリは **`/Users/fujiiisamusei/Projects/藤井勇成（ヘルスケア）/site`**。
  毎回 `git pull --ff-only origin main` してから始める（別セッションが先に push している）
- ローカルで動くので、リポジトリ・git の認証・Slack・Google カレンダーが全部そのまま使える
- **セッションを閉じても消えない。** チャットに紐づかない
- 発火のたびに新しいセッションになるので、**文脈は引き継がれない。**
  → だからプロンプトは薄く保ち、判断材料はこのファイルと `CLAUDE.md` に置く。
  プロンプトに事実を書き足さない。書き足すならここに書く

代償は1つだけになった。

**発火時刻に Mac とデスクトップアプリが起動している必要がある。**
閉じていた場合は次回起動時に遅れて実行される。夜が飛んだ翌朝は、①の手順1
（前夜以降の書き込みを先に `js/data.js` へ反映）が取りこぼしを拾う。

月に一度は「Scheduled」の一覧で最終実行日時を見る。止まっていたらこのファイルを渡して
同じ3つを作り直せる。

## ★ 手順0 — Slack の疎通確認（毎回・最初にやる）

2026-09-04 に Slack が2度この状態になった。**障害ではない。**
（以下はクラウド Routine 時代の記録。ローカル定時タスクは毎回まっさらなセッションで
起動するので「走っているチャットで既定オフに戻る」現象は原理的に起きない。それでも
**疎通確認と退避経路は残す** — 取れない理由が何であれ、黙って終わらないことが要件だから。）

```
ListConnectors(["slack"]) →  connected: true / enabledInChat: false
```

アカウント側の認証は生きていて、**このチャットに対してだけオフ**になる。
同時に同じ状態だったのは Gmail だけで、他の6コネクタは `enabledInChat: true` のままだった。
Slack と Gmail は**この会話の途中で追加した2つ**である。
→ **後から追加したコネクタは、走っているチャットでは既定オフに戻る**のが最も整合する説明。
断続的に見えたのは、会話が再開されるたびに保存済み設定（＝オフ）へ戻っていたため。

毎回いちばん最初にこれをやる。

1. `ToolSearch("+slack read_channel send_message")` で `slack_read_channel` /
   `slack_send_message` を取る（コネクタのサーバー名は環境で変わるので、名前を決め打ちしない）
2. 取れなければ Slack を諦め、**代わりに必ず次をやってから終わる**
   - `js/data.js` の `todayOne` だけは今日のぶんに更新して push する
   - Google カレンダー「RUN！！！」に当日イベントを作り、説明欄にメニューと
     「★Slackがこのチャットでオフのため #320 に投稿できなかった」と書く

**★黙って終わらないこと。** 本人から見て「21時になっても所見が来ない」だけの状態が最悪で、
Slackが切れているのか私が判断を保留したのかが区別できない。カレンダーは
`enabledInChat: true` が続いているので、退避先として使える。

## ① 朝 07:00 JST（cron `0 7 * * *` ローカル時刻）

1. `slack_read_channel` で #320 の未読を読む。前夜以降に本人の書き込みがあれば、

2. `js/data.js` の `schedule` から**今日の月日に一致する行**を取る。

聞くのは週2回まで。毎朝4項目を並べると、答えない日が続いたときに

## ② 夜 21:00 JST（cron `0 21 * * *` ローカル時刻）

1. `slack_read_channel` で #320 を読む（`oldest` に前回処理した ts を渡す）。
2. 本人の書き込みが無ければ**何も投稿せずに終わる。**
   催促しない。処方日の走行確率が処方の無い日より低いという実測がある以上、
   催促は逆効果である可能性が高い。
3. 書き込みがあれば `js/data.js` を更新する。
   - `dailyLog` に1行追記（`date` は `9/5` 形式）。`run` に要点、`note` に所見
   - ランがあれば `recentRuns` にも追記
   - `longRuns` の該当行を `done: true` にし、`km` を実測値に置き換える
   - 実測が来た項目だけ `metrics` / `highlights` を更新する
   - **`todayOne` を明日のぶんに書き換える**
   - `meta.lastUpdated` を今日の日付に
4. `node -e "global.window={};eval(require('fs').readFileSync('js/data.js','utf8'))"` で構文確認。
5. **ファイルを個別に指定して** commit し `main` に push。`git add -A` は使わない。
6. #320 に所見を投稿する。**3〜6行。** 良かった点1つ、直す点1つ、次にやること1行。
   判定を変えたならその理由を1行。

### ワークアウトログの読み方

本人は Apple Watch のログをそのまま貼ってくる。拾うのはこの順。

1. **平均HR が上限（現在145）以下か** — これが最優先。ペースではない
2. **Z1-Z2 の割合** — ただし週20kmを下回る間は制約変数として扱わない（`CLAUDE.md`）
3. **心拍回復**（終了直後 → 1分後 → 2分後）— 速ければ「攻めても大丈夫」側のシグナル。
   2分で −30bpm 前後なら良好
4. **距離が直近30日の自己最長の +10% 以内か** — 超えていたら意図的な判断として記録する
5. ラップの散らばり — 中盤だけ速い等は処方との乖離として指摘するが、
   **心拍が上限内なら止める理由にはしない**

## ★ 処方の出し方（2026-09-04 に実測で分かったこと）

**休養日を日付で指定しない。走る日も日付で固定しない。**

`CLAUDE.md` に自分で記録している数字がある。

> 処方日の走行確率 23.8% ／ 処方が無い日 37.3%。日付を指定すると13.5ポイント下がる。

それを知りながら「9/1〜2はラン休養」と日付で出し、**9/1 に 8.91km を走られた**。
本人の遵守の問題ではなく、処方の出し方の問題である。

- ✅「5〜6km を1本。9/5 か 9/6 のどちらかで」
- ✅「もう1本は脚が軽ければ。張っていれば休養に振替」
- ❌「9/5 に 6km」「9/1〜2 は休養」

**週の合計を埋めさせない。** 決めるのはロング走の刻みとイージーの本数だけで、
合計はそこから出てくる数字にすぎない。本数を減らしてよいと明示的に書く。

## 全部の起動に共通する約束

- ブランチは `main`。PR は作らない（`CLAUDE.md` の公開方針）。
- `git add -A` / `git add .` は使わない。**ファイルを個別に指定する。**
  このリポジトリは public で、一度 push すると回収できない。
- 顔写真・診断書 PDF・施術記録はリポジトリに置かない。
- 判断基準は `CLAUDE.md` の「コーチング判断フレームワーク」に従う。
  単発の1データポイントで「即休養」と言わない。主観申告をデータより軽視しない。
- **データが無い日は、無いと書く。** 推測で `dailyLog` を埋めない。
- **サイトの記録と実測が食い違ったら、実測を正として訂正し、訂正した事実を残す。**
  9/1 を「完全休養」と記録していたが実際は 8.91km 走っていた、という例が既にある。
- 迷ったら何もせず、#320 に「判断できなかった理由」を1行だけ残す。
  間違った更新を push するより、保留の方が安い。
