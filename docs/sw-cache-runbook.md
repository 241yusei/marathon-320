# Service Worker キャッシュ運用手順書 — JSファイル追加時に必ず読む

> 2026-07-29作成。対象: `sw.js`（PWA用サービスワーカー）。
> このリポジトリはビルドステップ無しの静的サイト（`README.md`・`docs/architecture.md` A-4を参照）で、
> `sw.js` の `CORE[]` と `CACHE` は完全にハードコードされている。JSファイルを追加する PR は
> 必ずこの手順を踏むこと。踏み忘れは「オフライン時・再訪時に古いサイトが表示される」という
> ユーザーからは気づきにくい形で事故る。

---

## 1. なぜこの手順が必要か

`sw.js` は起動時（`install`イベント）に `CORE[]` に列挙されたファイルだけを一括プリキャッシュする。
`CORE[]` は配列リテラルで手書きされており、`index.html` の `<script>` タグを自動的には読まない。

したがって、`index.html` に新しい `<script src="./js/xxx.js">` を追加しても、`sw.js` の `CORE[]` に
同じパスを追記しない限り：

- そのファイルは**プリキャッシュに載らない**
- 初回オンライン訪問時はネットワークから取得できるため気づきにくい
- しかし**オフライン時**や、Service Worker が古い `CACHE` を掴んだままの**再訪時**には、
  新ファイルがキャッシュに無いまま参照され、機能欠落・コンソールエラー・最悪ページ描画停止につながる

さらに `CACHE` のバージョン文字列（`m320-vN`）を上げないと、`activate` イベントの
「`CACHE` と一致しないキー（＝古いキャッシュ）を削除する」処理が発火せず、ユーザーのブラウザに
古いキャッシュが居座り続ける。**ファイル追加＝ `CORE[]` 追記＋`CACHE` 更新はセット**で行う。

---

## 2. JSファイル追加時の手順

新しい `.js` ファイルを追加する PR では、以下を順番に実行する。

1. **`index.html` に `<script>` タグを追加する。**
   `type="module"` は使わない（README が明示する「`file://` でブラウザから直接開くだけ」という
   運用と、ES Modules の `file://` CORS 制約が両立しないため。詳細は `docs/architecture.md` 0-4）。
   読み込み順（依存関係）に注意して既存の `<script>` 群の適切な位置に挿す。

2. **`sw.js` の `CORE[]` に同じパスを追記する。**
   `index.html` の読み込み順と `CORE[]` の並びを揃える（プリキャッシュの成否には順序自体は
   影響しないが、差分レビュー時に「何がどこに追加されたか」を目で追いやすくするため）。

3. **`sw.js` の `CACHE` を1つ上げる。**
   `m320-vN` → `m320-v(N+1)`。単純なインクリメントで、意味的なバージョニングはしない。

4. **`file://` で `index.html` を開いて動作確認する。**
   ブラウザのコンソールに `pageerror` や 404 が出ないこと、追加した機能が期待通り動くことを確認する。

5. **ブラウザの DevTools（Application タブ > Service Workers / Cache Storage）で、
   新しい `CACHE` 名（`m320-v(N+1)`）のキャッシュが生成されているか確認する。**
   合わせて、旧バージョンのキャッシュが `activate` 時に削除されていることも確認できるとなお良い
   （一度リロードすれば `caches.keys()` から旧キーが消える）。

この5点は `.github/pull_request_template.md` の「静的サイトの制約」チェック項目としても
レビュー時に必ず確認する。

---

## 3. なぜ自動化しないのか

`CORE[]` を `index.html` の `<script>` タグから自動生成すれば、この手順は不要にできる。
しかし、それには「ビルド時にHTMLをパースして配列を生成するスクリプト」＝**ビルドステップ**が要る。

このリポジトリは意図的にビルド無しを選んでいる（`docs/architecture.md` A-3・A-4、および
README の「ビルド不要の静的サイト。`index.html` をブラウザで開くだけ」という運用宣言）。
ビルドステップを導入すると、

- 「`index.html` を開くだけ」という運用が壊れる（ビルド生成物を都度作らないと `CORE[]` が古いまま）
- `main` ブランチに push すれば即 GitHub Pages に反映される、という現在の確実性が失われる
  （ビルドが失敗すればサイトが更新されない、または古いまま止まる）
- CI/CD の追加コスト（ワークフロー・依存関係・失敗時の切り分け）が発生する

これらは `docs/architecture.md` A-3「代償と対処」が明記した通り、**この設計が唯一手放したくない
制約**であるビルド不要性を崩す。したがって、`CORE[]` の生成・同期は自動化せず、
**手順書＋PRテンプレートのチェックリストで人間のレビュー時に担保する**方を選んだ。
手作業の手間よりも、ビルド不要という設計の根幹を守ることを優先している。
